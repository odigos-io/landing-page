Odigos Central already gave you one place to manage observability across Kubernetes clusters and VMs. Cloud Connectors extend that same control plane into your cloud accounts — so Lambda, Fargate, and Cloud Run stop being the missing hops in your traces.

## The gap after the cluster

Modern systems rarely live only in Kubernetes. A request often leaves a service mesh, hits an API Gateway, and lands in a Lambda — or fans out to a Fargate worker, or a Cloud Run service. On the cluster side, auto-instrumentation is straightforward. Outside it, teams still wire OpenTelemetry by hand: layers on every function, sidecars in every task definition, env vars copied across regions.

That work doesn’t scale, and the traces usually don’t either. You get a clean story inside the cluster, then a black box in the cloud.

## What Cloud Connectors are

[Cloud Connectors](https://docs.odigos.io/cloud-connectors/overview) are the third connection type in Odigos Central, alongside remote clusters and the VM Agent.

Each connector maps to one cloud account boundary — an AWS account or a GCP project. From Central you:

1. **Discover** instrumentable workloads in that account
2. **Choose** which ones to observe by creating Sources
3. **Track** instrumentation status as telemetry starts flowing

Nothing is instrumented until you create a Source. Discovery is inventory; Sources are intent.

## You stay in control of access

Cloud Connectors are not blanket admin access to your cloud. Scope is layered:

1. **IAM / service account permissions** — the role you grant defines which APIs the connector can call
2. **Connector capabilities** — per resource type, you choose discovery-only vs discovery + instrumentation
3. **Sources** — even discovered workloads stay untouched until you opt them in

Credentials live as Kubernetes Secrets in the Central cluster. One connector owns one account, so ownership and blast radius stay clear. For AWS, prefer Assume Role with an External ID over long-lived admin keys — see [Add an AWS Connector](https://docs.odigos.io/cloud-connectors/add-connectors/add-aws-connector).

## Managed by Odigos, or by your IaC

For each workload type you can choose:

| Mode | Who changes the resource |
| --- | --- |
| **Odigos-managed** | Odigos attaches and reconciles instrumentation (e.g. a Lambda layer, or a Fargate sidecar) |
| **Self-managed** | You apply changes via CloudFormation, CDK, or Terraform; Odigos discovers and reports status only |

Use Odigos-managed when you want instrumentation without touching pipelines. Use self-managed when IaC is the source of truth. Don’t do both on the same workload — reconcile fights are no fun.

## What’s covered today

| Provider | Discover | Instrument |
| --- | --- | --- |
| AWS Lambda | Yes | Yes (managed or self-managed) |
| Amazon ECS Fargate tasks | Yes | Yes (managed or self-managed) |
| Amazon ECS / Fargate clusters | Yes | Agent install coming soon |
| GCP Cloud Run | Yes | Yes |
| GKE / Compute Engine | Yes | Coming soon |

Language support depends on the workload — for example Lambda covers Java, Python, Node.js, and Ruby; Fargate adds .NET and PHP; Cloud Run covers Java, Python, Node.js, and .NET. Full matrices live in the [overview](https://docs.odigos.io/cloud-connectors/overview).

Instrumented cloud workloads export **OpenTelemetry over OTLP** to a destination you configure on the connector. That endpoint has to be reachable from the cloud environment itself (from Lambda’s network path, or from the Fargate task’s VPC) — not only from the Central cluster.

## Getting started

1. Install [Odigos Central](https://docs.odigos.io/central/overview) and [enable Cloud Connectors](https://docs.odigos.io/cloud-connectors/enable)
2. Add an [AWS](https://docs.odigos.io/cloud-connectors/add-connectors/add-aws-connector) or [GCP](https://docs.odigos.io/cloud-connectors/add-connectors/add-gcp-connector) connector with the access level you want
3. Wait until the connector is **Connected** and discovery finishes
4. Attach an OTLP destination, create Sources for the workloads you care about, and watch status flip to instrumented — details in [Instrument Cloud Workloads](https://docs.odigos.io/cloud-connectors/instrument-workloads)

## One control plane, every environment

Clusters, VMs, and cloud accounts used to mean three different instrumentation stories. Cloud Connectors fold the cloud side into the same Central UI — discover, select, instrument — without giving up least-privilege access or your existing IaC workflows.

Ready to close the gap? Start with the [Cloud Connectors documentation](https://docs.odigos.io/cloud-connectors/overview), or [get a demo](https://odigos.io/) if you want to see it on your accounts.
